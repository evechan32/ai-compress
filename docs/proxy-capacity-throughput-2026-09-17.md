# 代理实验：容量 → 吞吐（不需要插件）2026-09-17

## 目的

回答一个关键质疑：**我们驱逐后拿到的容量增益，为什么没兑现成吞吐？是方法限制还是负载假象？**

做法：用 stock vLLM（0.11.2，3090）直接扫 `gpu_memory_utilization` 人工制造不同 KV 容量，
在三种负载形状下测吞吐。**这样测的是"给定一份容量，能兑现多少吞吐"**，与插件的实现细节无关。

## 结果

| 负载形状 | gmem 0.30 | gmem 0.45 | gmem 0.60 | gmem 0.80 |
|---|---|---|---|---|
| **S1** prompt 1152 / gen 512 / M=128 | 2051 tok/s | **3369（1.64×）** | 3395（1.66×） | 3255（1.59×） |
| **S2** prompt 4507 / gen 1500 / M=32 | 672 | **1258（1.87×）** | 1140（1.70×） | **1258（1.87×）** |
| **S3** prompt 1152 / gen 1500 / M=64 | 1865 | 2401（1.29×） | **2613（1.40×）** | （缺） |

容量换算：`gmem 0.30→0.45` 增加 `(0.45−0.30)×24GB = 3.6GB` KV；
基线 KV（0.30 时）≈ `0.30×24 − 权重 3.1 − 激活` ≈ 3.5GB → **容量约 2.03×**。

## 结论

1. **容量确实能兑现成吞吐，且幅度大**：~2.03× 容量 → **1.64×（S1）/ 1.87×（S2）**。
   ⇒ 此前"系统变成 compute-bound 所以兑现不了"的**解释是错的**（S2 在 gmem 0.80 仍在涨）。
2. **S2（长 prompt + 长生成）兑现最好（1.87×）**，S3（长生成但短 prompt）最差（1.40×）。
3. **我们插件存在可量化的缺口**：

   | 路径 | 容量增益 | 吞吐增益 | 兑现率 |
   |---|---|---|---|
   | stock vLLM（一开始就有容量） | ~2.03× | **1.64×** | 81% |
   | 我们插件（prefill 后才释放） | ~1.94× | **1.26×** | 65% |

## 诊断

差别在**释放的时机**：

- 代理实验：容量**从一开始就够** → 整个 prefill 阶段就能跑更高并发
- 我们的插件：prefill 阶段池子仍被未驱逐的全量 prompt 占满 → **峰值不变** → 早期并发度与不驱逐时一样，
  只有进入 decode 尾段才享受释放

⇒ 收益只兑现了 decode 段。prefill 占墙钟比例越高的形状，兑现越少（S1）。

## 由此确定的改动优先级

| # | 改动 | 作用 |
|---|---|---|
| **1** | **prefill 中途驱逐**（分块打分 + 提前释放） | **降峰值** → 补齐那 ~30% 兑现缺口 |
| **2** | **生成段窗口**（每 decode 步释放超窗块） | 让长生成 KV 有界，消除"只压 prompt 段"的天花板 |
| 3 | 两者都要 vLLM 端实现 | 移植可行性已验证：vLLM 0.11.2 里 `KVCacheSpec`/`FullAttentionManager`/`remove_skipped_blocks`/`TritonAttentionBackend`/`ModelRunnerOutput` 齐全，仅 `rswa_prefix_lens` 缺失需重写 |

## 复现

```bash
# 3090 上（vLLM 0.11.2 + torch 2.9.0 target 环境，见 docs/vllm-on-old-driver-sm86-recipe.md）
PYTHONPATH=/hy-tmp/t29 VLLM_USE_FLASHINFER_SAMPLER=0 \
  python3 bench/proxy_capacity_sweep.py --m 32 --prompt-tokens 8000 --gen-tokens 1500 \
  --gmem 0.45 --max-len 16384 --tag S2-g0.45
```
