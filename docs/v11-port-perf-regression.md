# 0.11.2 端口性能回退定位（2026-09-18）

## 结论

**功能移植正确、但性能有回退**：插件在 0.11.2 上把吞吐从 3331 拉到 2135 tok/s（**0.64×**），
而 0.28 上同配置是 **1.12–1.26× 增益**。回退不是方法问题，是**移植引入的开销**。

## 隔离实验（M=128, prompt≈1152, gen=512, gmem=0.30, 3090）

| 配置 | tok/s | vs off | 说明 |
|---|---|---|---|
| `off` | 3331 → 3270 | 1.00× | 基线 |
| `chunkkv@1.0` | 2493 | **0.76×** | **只打分**（保留全部 → 不释放、不压实） |
| `chunkkv@0.9` | 1975 | 0.60× | 打分 + 释放 + 压实 |
| `chunkkv@0.3` | 2135 | 0.64× | 原目标配置 |
| `chunkkv@0.3 + genwin256` | 2110 | 0.63× | gen=512 太短，窗口(256)看不出收益 |

⇒ **打分 ≈ −24%**，**释放+压实 ≈ −16%**。0.28 上打分开销实测约 −5%，差一个量级。

## 怀疑的开销来源（按可能性排序）

1. **打分里的 CPU-GPU 同步**：`md.query_start_loc.tolist()` / `md.seq_lens.tolist()`
   每次打分调用都做 2 次同步；128 请求 → 256 次同步落在关键路径上。
2. **逐请求 Python 循环**：`for r in range(len(seqlens))` 里做 gather + einsum，
   未向量化；128 请求 × 1 次打分，每次含多次小 kernel 启动。
3. **Builder 每个 attention 层、每个 decode 步都跑**：我们的后端类可能让每个层
   各自持有一个 builder 实例 → 压实循环（clone + 逐行重建）被放大 ×层数×步数。
   即使 `idx == range(nblk)`（无变化）也会走一遍 clone 与循环。
4. **`torch.tensor(idx, device=bt.device)`**：逐行从 Python list 建 GPU 张量
   （128 行/步），每次都是一次 H2D 小拷贝。

## 下一步优化（按性价比）

1. **Builder 加"保留集版本号"缓存**：`_PE_VERSION` 未变则直接返回 md（0.28 里有
   `_PE_VERSION`，移植时没带过来）。gw=0 时保留集是常量 → 可只压实一次。
2. **打分去掉同步**：把 `tolist()` 换成切片张量运算，或只在必要时同步一次。
3. **打分向量化**：把逐请求循环改成批处理（或至少缓存 block_table 切片）。
4. **仅在目标层构建自定义 builder**：避免所有层共用我们的 builder。

## 尚未测（gen 窗口的真正收益场景）

`gen=512` 太短，256 窗口覆盖不到多少生成块。要验证生成段窗口的收益，
需用**长生成**形状（如 M=64, prompt≈1152, gen=1500–4000），此时：
- 不压生成段时 KV 随生成线性增长 → 容量被吃光
- 压生成段后 KV 有界于 `O(prompt×keep + W)` → 容量与吞吐应显著改善
