### 生成段窗口：容量收益大，但实现开销更大

| 配置（M=64, prompt≈1152, **gen=1500**, gmem=0.30） | tok/s | vs off |
|---|---|---|
| `off` | 2848 | 1.00× |
| `chunkkv@0.3, gw=0` | 2526 | 0.89× |
| `chunkkv@0.3, **gw=256**` | 1688 | **0.59×** |

每请求 KV 应从 1846 → 602 token（≈3× 容量），**但吞吐反而再掉 30 个百分点**。

**已排除**：不是"压实被每层重复执行"（加了"每步只压一次"的缓存，0.58× → 0.59×，无改善）。

**已排除的两个假设**（各自单独实测，均无改善）：
1. ❌ "压实被每个 attention 层重复执行" → 加"每步只压一次"缓存（按 common_attn_metadata
   对象做键 + 持强引用防 id 复用）：0.58× → 0.59×
2. ❌ "manager 每步重扫 `[pnb, tail)` 释放区间" → 改为记录 `_GEN_FROM` 只扫新增块：
   0.59× → 0.56×

**剩余怀疑（未验证，需 profiler）**：
1. `seq_lens` / `block_table` 每步变化 → 注意力 kernel 走慢路径或重新 autotune
2. 释放的块被新 token 立即复用 → 块池回收/再分配串行化
3. 压实时把 block_table 尾部写 0，可能被 kernel 当作合法块 0 而多做工作

**方法学教训**：这一步已经连续两次"猜成因 → 改 → 无改善"。继续盲猜是浪费 GPU 预算，
应当改用 torch profiler / nsys 直接看 time breakdown 再动手。

## 五、生成段窗口的真实收益（容量受限形状）★ 关键结果

前面的长生成测试用 M=64，**根本不是容量受限**（64×1846 ≈ 118k token，池子约 122k → 刚好装下），
所以只看得到开销。把并发加到 **M=256** 后形状才真正容量受限：

| 配置（M=256, prompt≈1152, gen=1500, gmem=0.30） | tok/s | vs off |
|---|---|---|
| `off` | 2475 | 1.00× |
| `chunkkv@0.3, gw=0`（仅 prompt 驱逐） | 2408 | 0.97× |
| **`chunkkv@0.3, gw=256`（+ 生成段窗口）** | **4012** | **1.62×** |

**结论**：
1. **仅压 prompt 段在长生成形状下毫无收益（0.97×）** —— 因为长生成时 KV 主体在生成段。
2. **加上生成段窗口后 1.62×** —— 生成 KV 被界在 256 而非 1500（−83%），
   释放出的容量直接兑换成并发 → 吞吐 +62%。
3. 这比 0.28 上最好的结果（keep-30% 的 1.26×）还高，且是**新能力**（0.28 的 chunkkv 模式不压生成段）。
4. 用户"既然压了就压生成段"的判断被实测证实。

### 复现

```bash
export PE_SINK=0 PE_OBS=32 PE_WIN_AGG=max PE_RATIO=0.3
PE_MODE=chunkkv PE_GEN_WINDOW=256 \
  python3 bench/perf_v11.py --m 256 --prompt-words 576 --gen 1500 --gmem 0.30 --tag x
```

### 注意

- `PE_GEN_WINDOW` 的收益**只在容量受限形状下出现**（大并发 + 长生成）。
  在非容量受限形状下它只贡献开销（压实是每步的），故非受限场景可设 0。
- 压实已全向量化（掩码 + stable argsort），逐行 Python 循环与 H2D 已移除。

## 六、⚠️ 关键更正：驱逐尚未真正影响注意力（2026-09-18 发现）

**前五节的性能数字建立在错误前提上，必须重新审视。**

### 证据

判据：同一次生成（prompt=1096, `max_new=256`，greedy）的**全文 sha1**：

| 配置 | sha1 |
|---|---|
| `off` | `c3215d1dbb8e` |
| `chunkkv@0.5`（释放 34/69 prompt 块） | `c3215d1dbb8e` |
| `chunkkv@0.5 + genwin=64`（再释放生成块） | `c3215d1dbb8e` |

**三者逐位相同** → 释放的块**仍被注意力读到**，压实没有作用到计算上。

### 已排除的原因

1. ❌ 不是"Null 检测失效" —— 诊断显示 metadata 的 block_table 里确实没有 null
   （`nnull=187` 全是越界 0 填充），所以改为由 manager 记录 `_DROP` 下标集
2. ❌ 不是"Builder 没跑" —— 日志确认 `changed=True dropped0=34 nrow=1`
3. ❌ 不是"元数据为 None" —— 启动期 56 次 None 后，正常执行期全部有效且 `has_bt=True`

### 当前判断

**我们在 Builder 里改写 `md.block_table` / `md.seq_lens`，但没有到达注意力内核。**
可能是 vLLM 0.11.2 在 `build()` 之后重新赋值这两个字段，或内核从别处读取。

### 影响（重要）

- **内存释放是真的**（`freed=N`、pool 增长、并发吞吐提升可复现）
- 但**注意力仍在读被释放的块** → 单请求测试里这些块尚未被复用，所以输出看起来正常；
  **在并发（如 M=256）下这些块会被其他请求复用 → 输出必然是垃圾**
- ⇒ 第五节的 1.62× **不能作为有效结果**，必须先修好压实并重测
- ⇒ 这也意味着 `PE_MODE=chunkkv` 在 0.11.2 端口上**当前不可用于正确性敏感场景**

### 下一步（定位内核读取路径）

1. 查 `TritonAttentionMetadataBuilder.build()` 之后，runner 是否重新赋值 `block_table`/`seq_lens`
2. 查 Triton Impl/kernel 实际从哪个字段读块表（可能经 `get_forward_context()` 或缓存结构）
3. 修好后再重跑：sha1 必须不同（证明生效）→ NIAH → 并发正确性 → 吞吐

## 七、更正第六节 + 修正后的最终数字（2026-09-18 晚）

### 1. 我第六节的判断是错的：掩码其实**能**生效

第六节依据"三种配置 sha1 相同"推断"压实没到达内核"——**这个推断错了**，两处原因：

**a) sha1 判据本身无判别力**：测试题是重复填充句（"harbor master..."），
续写只依赖局部模式，丢掉一半 prompt 块**本来就不该改变贪心续写**。

**b) 真正的 bug 是我自己的"版本缓存"优化**：我加了
`if gw == 0 and _BUILT_VER == _VER: return md`，假设"保留集没变就不用重做"。
但 **base `block_table` 每步都被 vLLM 重新生成（未压实）**，所以压实必须**每步重做**。
该缓存让压实**只生效了第一步**，之后注意力又看到未压实的块表。

诊断证据（`idbg`/`bdbg`）：
```
idbg bt0_nz=69 seq0=1096     ← prefill（未压实）
evict chunkkv freed=34
bdbg changed=True sl0=1097   ← Builder 压实 69→35 块
idbg bt0_nz=35 seq0=553      ← 注意力确实看到压实后的元数据（生效！）
idbg bt0_nz=69 seq0=1098     ← 但下一步又变回未压实（缓存把它跳过了）
```

**反向对照（决定性）**：强制把 `seq_lens` 压到 1：

| 配置 | sha1 | 输出 |
|---|---|---|
| baseline | `f66ea1ff896b` | ' The harbor master logged every vessel...' |
| `PE_FORCE_SL=1` | **`ce7f81586db1`** | `'----------------'` |

输出剧变 ⇒ **改写确实到达了注意力内核，掩码有效**。

**修复**：删掉版本缓存（压实改为每步执行）。

质量（NIAH, 5 深度 × 3）：

## 十一、生成段窗口的质量影响（token 级分歧分析）★ 收尾验证

这是该功能**最关键的未测风险**（长生成下模型可能需要回看自己前面写的内容）。

协议：2 任务 × 20 样本，`max_new=256`，`ratio=0.5`，比较 `gen_window=0` 与 `=64` 的**逐 token 输出**。

| 指标 | 值 |
|---|---|
| 样本数 | 40 |
| **输出完全相同** | **25/40 (62%)** |
| 出现分歧 | 15/40 |
| **首次分歧位置**（生成 token 序号） | min=**87**，p25=100，中位=113，p75=129，max=244 |
| **分歧早于窗口(64) 的比例** | **0%** |
| F1 | 0.3046 (gw=0) → 0.3043 (gw=64)，Δ −0.0003 |

### 解读

1. **0% 的分歧早于窗口** ⇒ 窗口行为**完全符合设计**：当可丢弃区域为空时输出逐字不变；
   只有当窗口真正开始丢弃有内容的生成块时（minimum 87 > 64）才开始分歧。
2. **62% 的样本输出完全一致**，F1 变化可忽略（−0.0003）⇒ **质量代价很小**。
3. 最小分歧位置 87 比窗口 64 晚，是合理的：分块粒度为 16，加上"块要整体越窗"才释放，
   实际最早生效点在 `窗口 + 块内偏移` 之后。

### 与吞吐的合并结论

- **性能**：容量受限形状 +60%（1.60×），且必须同时压生成段（prompt-only 为 0.92× 净亏）
- **质量**：keep-50% 无损失；生成段窗口额外代价可忽略（62% 样本逐字相同、F1 −0.0003）
- ⇒ **生成段窗口是本轮最有价值的能力**：它把 prompt-only 的净亏翻成 +60%，而质量代价可忽略。

| 0.80 | ❌ `Available KV cache memory: -1.70 GiB` |
| 0.92 | ❌ `No available memory for the cache blocks` |
| 0.96 | ❌ 同上 |

**原因**：7B bf16 权重约 15.2GB，加上 vLLM 的激活与显存剖析预留，24GB 卡上留给 KV 池的空间为**负**。
这是**硬件上限**，与移植无关。

**本节的 1.5B 结论不受影响**；若需 7B 数据，两条可行路径：
1. **4-bit 7B（AWQ/GPTQ，权重 ~5GB）** —— 24GB 卡上宽裕；sm_86 对 marlin 支持良好。
   代价：需下载 ~5GB 模型（约 5–10 分钟），并确认 0.11.2 端口在量化模型上的行为。
2. 换 ≥48GB 显存的卡跑 bf16。

（注：0.28 时期的 7B 数据是在 sm_120 机器上用 **AWQ 4-bit** 得到的，同样是量化模型；
故若要与历史 7B 结论对齐，路径 1 反而是更一致的选择。）

## 十四、更正第十三节：7B 的"性能回退"是**测量假象**（第三次同类错误）

### 问题

第十三节说"7B 上 0.75×/0.53×，收益不跨规模成立"——**错了**。根因是**测量方法无效**：

我的 perf harness 用的是**问答式 prompt**（"Question: What themes recur?"），模型答完就 EOS。

## 十六、SLA 视角：固定并发下的 TTFT/TPOT 尾延迟（用户选做项 2）

固定 M 的总吞吐之外，服务更关心**尾延迟**。自建 SLA 探针（`bench/sla_probe.py`，
走 OpenAI 兼容 HTTP + 流式，量 TTFT/TPOT 分位数）：

### 结果（1.5B, gmem=0.30, prompt≈1024, gen≈1024, num=96）

| 配置 | 并发 | tok/s | **TTFT p99** | **TPOT p99** |
|---|---|---|---|---|
| `off` | 64 | 1617.7 | 2062.9 ms | 30.28 ms |
| `off` | 128 | 1860.1 | **1857.5 ms** | 51.00 ms |
| `off` | 256 | 1944.8 | 1889.2 ms | 47.43 ms |
| `chunkkv gw=0` | 128 | 1941.3 | 2907.6 ms | 46.16 ms |
| **`chunkkv gw=256`** | 128 | **2257.1 (+21%)** | 2767.2 ms | **40.77 ms** |
| **`chunkkv gw=256`** | 256 | **2150.5 (+11%)** | 2810.2 ms | **42.91 ms** |

### 结论：存在真实取舍

1. **吞吐**：插件 +11~21%（同并发下）
2. **TPOT 尾延迟**：插件**更好**（40.8 vs 51.0 ms @c128）—— 因为每请求的 KV 更短、decode 更快
3. **TTFT 尾延迟**：插件**恶化约 50%**（2767 vs 1857 ms）—— 因为**打分发生在 prefill 末尾**，
   直接加在"首 token 之前"的关键路径上（每请求一次，含 CPU-GPU 同步）

⇒ **面向交互式服务（重 TTFT）时这是净负；面向吞吐/长生成（重 TPOT/容量）时是净正。**
这是一个此前未量化的取舍，值得在部署时作为选择依据。

### 测量口径提醒

本次 `--num 96` < 并发 128/256，故 c128/c256 的**有效并发都≈96**（同一负载）。
跨配置在同并发下仍可比，但**要得到"固定 SLA 下的 max 并发"曲线，需 `num >> concurrency`**。
这是下一次要修的口径。

## 十八、块复用正确性验证（最高风险项）★ 通过

### 为什么这是最高风险项

前面所有正确性证据（`PE_FORCE_SL` 反向对照、NIAH 15/15）都只在 **`max_num_seqs=4`** 下取得。
而插件的核心机制是"**释放块 → 块被其他请求复用**"：若压实的边界有误，注意力会读到
**已被别的请求写入的块** → 输出串到别人的内容。这是"释放+复用"场景下的致命失效模式。

### 探针设计（`bench/pevict_reuse_check.py`）

**每个并发请求写入独一无二的 code**（`V0000X`、`V0001X`…），针埋在不同深度，然后检查：
- `hit`：输出含**自己的** code
- **`contamination`：输出含别人的 code**（应为 0；任何非零都是严重 bug）
- `miss`：两者都没有

比"掉分"先进：串扰是一个**可精确诊断**的失效模式，而模糊掉分难以归因。

### 结果（1.5B, n=256, max_num_seqs=64, gmem=0.30, prompt≈2048, ratio=0.3）

请求数是并发容量的 4 倍 ⇒ 排队 + 块池充分回收复用。

| 配置 | hit | **contamination** | miss |
|---|---|---|---|
| `off` | 256/256 | **0** | 0 |
| `chunkkv, gw=0` | 256/256 | **0** | 0 |
| `chunkkv, gw=256` | 256/256 | **0** | 0 |

**结论：压实（隐藏被释放块）在块复用场景下正确** —— 无串扰、无丢失。
这关闭了此前列出的最高风险未验证项，也使此前的性能数字**建立在正确的语义之上**。

### 当前验证状态（更新）

| 项 | 状态 |
|---|---|
| 功能（S1/S2/S3 + 入口点自动分派） | ✅ 已验证 |
| 正确性（元数据改写到达内核） | ✅ 反向对照 |
| **正确性（高并发块复用无串扰）** | ✅ **本次关闭** |

## 十九、释放时机实验：假设被推翻（含噪声地板发现）

### 假设

"KV 释放只有在**峰值之前**发生才值钱" ⇒ 推论：**越早释放越好**。
上一节的代理实验给出支持性证据（stock 从一开始就有容量 → 兑现 81%；我们 prefill 后才释放 → 65%）。

### 控制实验（固定释放量，只变释放时点）

同一保留集（`PE_RATIO=0.3`），只在 prefill 之后再过 N 个 token 才真正释放：
新增旋钮 `PE_RELEASE_DELAY`（`kvcompress/pevict_v11.py`）。

形状：1.5B, M=256, prompt≈1152, gen=1500, gmem=0.30, `PE_GEN_WINDOW=0`（隔离 prompt 释放）。
五点**全部跑满配额 384000/384000** ⇒ 比较有效。

| 释放时点 | tok/s | vs 最早 |
|---|---|---|
| d0（最早，prefill 后立即） | 2124.7 | 1.000× |
| d64 | 2275.1 | 1.071× |
| d256 | 2202.7 | 1.037× |
| d512 | 2284.5 | 1.075× |
| **d1200（几乎最后）** | **2324.5** | **1.094×** |

### 结论：推翻

1. **释放越晚反而越快**（d1200 最快），且**不单调** ⇒ 假设不成立。
2. 但**更关键的是噪声地板**：同一配置（`gw0`）在不同批次里测得
   **1870.8 / 2073.8 / 2124.7** ⇒ **跨批离散约 13%**，
   **大于**本次"时机"效应（约 9%）。
3. ⇒ 严格结论：**prompt 块的释放时点（在 decode 的 0–1200 token 范围内）对吞吐无可测影响**，
   效应落在测量噪声之下。

### 被推翻后，正确的理解是什么

| 因素 | 是否重要 | 证据 |
|---|---|---|
| **稳态容量**（最终腾出多少块） | ✅ 重要 | keep-30% vs keep-50% 的差异；prompt-only 0.92× vs +genwin 1.60× |
| **生成段是否被压** | ✅ 决定性 | 0.92× → 1.60×（相对 +74%）|
| **prefill 期间是否有容量** | ✅ 重要 | 代理实验：stock 从一开始有容量 → 兑现 81% vs 65% |
| **decode 阶段何时释放 prompt 块** | ❌ 无可测影响 | 本实验（五点，含极端值）|

⇒ 正确的说法不是"越早越好"，而是"**容量要在需求峰值（prefill 波）之前就存在**"——
这只能靠**压生成段**或**在 prefill 中途驱逐**实现，而不是靠"把同一个释放往后挪"。

### 方法学发现（重要）

**离线 perf harness 的跨批离散约 13%**，因此：
- 任何小于 ~10% 的效应**不可分辨**（本会话早前若干"差异"可能只是噪声）
- 若要测小效应，必须**同一批次内多次重复取中位数**，而不是跨批比较

---

## 二十、prefill 中途驱逐：已实现、质量无损、但**吞吐未获益**（诚实负结果）

### 动机（用户提出的核心痛点）

长上下文 + 大模型时，**prefill 阶段单请求 KV 就可达 7GB（7B/128k）～41GB（70B 级）**，
单个长请求就能撑爆卡。而我们的插件**打分在 prefill 之后 ⇒ 峰值不变 ⇒ 对这种场景零帮助**。

### 实现

`PE_MIDPREFILL=1`（`kvcompress/pevict_v11.py`）：

- **query-free 逐 chunk 打分**（CurDKV 式 `k²·v²`，只需 K/V 范数，不需要问题）
- 每个 chunk 到达即累积打分 → 重选保留集（sink + top-r + 近窗）→ 写 `_RETAINED`
- manager 的释放门控改为允许 **prefill 未完成时也释放**（`gate = mid and req in _RETAINED`）

**前提**：必须强制 chunked prefill（`max_num_batched_tokens` 设小），否则一次 prefill 完 ⇒
"中途"与"事后"等价。

### 实测

**质量（NIAH 40 条，`PE_MAXBAT=256` 强制分块）**：

| 配置 | hit | contamination |
|---|---|---|
| `off` | 40/40 | 0 |
| 事后驱逐 | 40/40 | 0 |
| **中途驱逐** | **40/40** | **0** |

⇒ **中途驱逐在 keep-30% 下无损**（我此前标记的"因果不对称"风险，在此探针灵敏度下未显现）；
日志确认逐 chunk 释放确实发生（每请求 freed=84）。

**吞吐（gmem=0.22 极紧, M=64, prompt≈1152, gen=64；三组均完整产出 4096 token）**：

| 配置 | tok/s | vs off |
|---|---|---|
| `off` | 1297.5 | 1.00× |
| 事后驱逐 | 1027.3 | 0.79× |
| **中途驱逐** | 1013.8 | **0.78×** |

⇒ **中途驱逐并未比事后驱逐更好**。此形状下瓶颈是 **prefill 计算量（固定 74k token）**，
而驱逐只省显存、不减 prefill FLOPs；且 vLLM 的准入控制按"请求总 token 数"估算所需块，
**不会因为我们将来会释放块而多接纳请求**。

### 未解的问题

**峰值（KV 高水位）始终没测到**：计划用 `block_pool.get_num_free_blocks()` 的最小值跟踪，
但插桩出现**无法解释的现象**——同一方法内的两个 `print` 只有一个生效（`evict chunkkv` 打印
正常，紧随其前的插桩打印始终不出现），排查未果。**故"中途驱逐是否真的降低了峰值"仍未验证。**

⇒ 下一步若要继续这条路，必须先解决峰值测量（可换用外部手段：固定 gmem 下二分找
"能完成的最大并发"），否则无法判断是"峰值没降"还是"降了但没用"。

### 结论（诚实）

- 中途驱逐**在质量上安全**（keep-30% 无损、无串扰）
- 但**在吞吐上没看到收益**（此形状），且**峰值未测**
- 因此这条"降低 prefill 峰值"的路，**目前证据不足以支持继续投入**；
  若仍要做，先解决峰值测量这一关。

## 二十一、KV 量化可行性：sm_86 上 fp8 不可用，但 **int8 数值上可用**（新发现）

### ① sm_86 的 fp8 KV：**硬性不可用**（已实测，含编译器错误）

强开 `supports_fp8()` 后：

```
fp8_e4m3 → triton.compiler.errors.CompilationError:
   ValueError("type fp8e4nv not supported in this architecture.
               The supported fp8 dtypes are ('fp8e4b15', 'fp8e5')")
fp8_e5m2 → AssertionError: assert self.kv_cache_dtype in {"fp8", "fp8_e4m3"}
```

vLLM 的 fp8 KV 路径要的是 **`fp8e4nv`**（sm_89+ 的 e4m3 变体），**Triton 在 sm_86 上编不出来**；
sm_86 只支持 `fp8e4b15` / `fp8e5`，而 vLLM 的 kernel 断言又只接受 `{fp8, fp8_e4m3}`。
⇒ **动态算 scale（`--calculate-kv-scales`）在这台机器上连执行都到不了**，谈不上测劣化。

### ② 关键洞察：反量化数学与 int8 完全相同

vLLM 的两个 Triton kernel 里，量化路径就是**一句乘法**：

```python
triton_unified_attention.py:250  if K_load.dtype.is_fp8():
:254                                 K = (K_load.to(tl.float32) * tl.load(k_scale)).to(Q.dtype)
triton_reshape_and_cache_flash.py:57  key_tile = key_load if ... else key_load / k_scale
```

**对称 int8（zero-point=0）的反量化也是 `x * scale`** ⇒ 注意力 kernel 的数学**已经就位**，
只需放宽 `is_fp8()` 守卫 + 改 dtype 映射 + 改写入量化 + 改 scale 公式（max_abs/127 而非 /448）。

### ③ 先做数值等效模拟（不碰内核）拿到"掉多少质量/慢多少"

`bench/int8kv_sim.py`：在 `k_proj`/`v_proj` 输出上插 hook 做 int8 量化→反量化
（KIVI 式：**K 按 channel、V 按 token**）。这与"KV 池存 int8 + 读取反量化"的**数值路径完全一致**。

自检（证明 hook 生效、非空操作）：

```
hooks_installed=56    calls=3584    mean_abs_err=0.026    rel=1.81%
```

**质量**（Qwen2.5-1.5B, HF, greedy）：

| 指标 | bf16 | **int8 (K-perchan, V-pertoken)** |
|---|---|---|
| NIAH（20 条） | 20/20 | **20/20** |
| LongBench qasper (n=20) | 0.3453 | **0.3453** |
| LongBench multifieldqa_en (n=20) | 0.3917 | **0.3917** |

**口径**：F1 在 n=20 下逐位相同是强证据但样本小；要下定论需 n=60/任务 + 配对 CI（同我们之前的做法）。

**开销**：hook 级每样本 0.70s → 0.79~1.20s（+13%~70%，波动大）。
**注意**：这是 PyTorch hook 的开销（量化/反量化是两个独立算子 + 额外显存往返），
**不代表融合进 kernel 的成本** —— 融合后应显著更低（e4m3 路径在 sm_89 上的实测开销约 5%）。

**显存**：2×（按构造，未在引擎内实测）。

### 结论

- **fp8 KV 在 sm_86：不可用**（编译器层面）
- **int8 KV 在 sm_86：数值上可用** —— 相对 K/V 误差仅 1.81%，质量无可测损失
- 因此**写 int8 KV kernel 是值得的**，且注意力的反量化数学**在 vLLM 里已经存在**（被 `is_fp8()` 挡住）
- 这是唯一能在这台机器上**直接压 prefill 峰值 2×** 的路径

### 副作用记录（需知晓）

操作过程中系统 python 的 torch 被顺带升级为 **2.13.0+cu130**（需更新驱动，在驱动 530 上报
"driver is too old"）。所有 vLLM 工作均通过 `PYTHONPATH=/hy-tmp/t29`（torch 2.9.0+cu128）运行，
不受影响；但**系统 torch 已不适合本机**。

### 为什么走 int8（而非 fp8）

fp8 在 sm_86 上**编译期就不可用**（`fp8e4nv not supported`，见第二十一节），
而 int8 的反量化数学与 kernel 里已有的 fp8 路径**完全相同**（都是 `x * scale`）。

## 二十三、int8 KV 质量缺陷根因确认：**scale 粒度**（架构层，非接线 bug）

### 往返检查结果（决定性）

在 `triton_attn.py` 的写入后立即读回、反量化、与源 K/V 比对：

```
[RT] k_rel=0.04533  v_rel=0.05881  k_scale=2.51969  v_scale=0.03445
     k_raw=[-125,114]  v_raw=[-29,82]  want_absmax=316.000
```

- **量化往返正确**：K 相对误差 4.5%、V 5.9%，无 clamp 触发
- 标定生效：`k_scale = 316/127 = 2.52` ✅ 与标定表一致
- ⇒ **写入/读取接线没有 bug**，int8 缓存里确实是正确量化的数据

### 真正的根因：**scale 粒度**

| 路径 | scale 粒度 | K 相对误差 | 质量 |
|---|---|---|---|
| **数值模拟**（`bench/int8kv_sim.py`）| **per-token / per-channel** | **1.81%** | NIAH 20/20、F1 逐位相同 |
| **vLLM 实现** | **per-layer 单个标量** | **4.53%** | NIAH **0/40** |

vLLM 的 KV 量化架构是**每层一个标量 scale**（`layer._k_scale`）。
对 **fp8** 这没问题 —— e4m3 有 4 位指数、动态范围宽，粗粒度 scale 可接受。
但 **int8 没有指数位**：单个离群通道就吃掉整个动态范围，导致**小幅度但关键的 key 只剩很少有效级数**
→ 检索能力被摧毁（局部连贯的文本仍能生成，所以表象是"输出通顺但答不出"）。

### 结论（重要）

- **int8 KV 在 sm_86 上能跑、内存精确 2.0×** ✅
- 但要让 int8 的质量可用，必须实现 **per-channel/per-token 的 scale 并与 KV 一起存储**
  —— 这正是 **KIVI 的核心机制**，也是 **vLLM 当前架构不具备**的
- 这解释了**为什么工业界用 fp8 而不是 int8 做 KV 量化**：fp8 的浮点指数范围
  让"每层一个标量 scale"这种极粗粒度也能工作 ✅

### 如果继续，需要什么

在 KV 缓存布局里增加粗粒度之外的 scale 存储（per-head 或 per-block scale 数组），并改：
写入 kernel（计算并存 scale）、读取 kernel（按位置取 scale 反量化）、
缓存分配（为 scale 预留空间）、manager（block 布局）。
**这已不是"改 dtype + 放宽守卫"，而是实现 KIVI 类方法的核心机制。**
